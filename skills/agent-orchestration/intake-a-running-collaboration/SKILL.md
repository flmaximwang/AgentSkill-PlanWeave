# 接手一段已经在跑的协作（你是后进来的那个）

## When to Use

- 用户把你 @ 进一个 thread，而里面**另一个 agent / 别的人已经在做**这件事（典型开场：「come and help us」）。
- 你被要求「看一下现在到哪了 / 帮忙盯一下 / 把状态写下来」，而工作**正在同时进行**。
- 你要复核另一方的进度主张，并且**不能碰**他正在跑的东西。

不适用：任务还没开始（那是普通接单）；你就是要亲手做那件事（那是执行方，不是接手方）。

- **会话上下文变长**（跨了 3+ 回合 / 要向接手的人解释背景 / 多条线并行）时：先把后续规划、子代理分配与执行都落成 plan 的块，再按块推进 —— 动作见 `maintain-a-shared-plan` 的「会话一长，先把它落到 plan 上」。

## 硬前提

1. **先确认你是哪一半。** 同一个 thread 里常有多个 bot（执行方、台账方、记录员）。不要跟对方抢同一个动作：
   他跑着的进程、他正在写的产物一律不碰。你的产物是**记录**（共享 plan / 状态文档），不是他的动作。
2. **不采信自述，也不替对方定罪。** 他给的结论（「活库未被写入」）与你实测到的（mtime、计数）分开写：
   实测支持就注明来源，没测到就标「待确认」。
3. **每个动作先算成本。** 这类 thread 里通常已经有人因为一次重查询拖垮了机器而被批评过。

## 步骤

### 1. 读 thread，但先压成可读的一页

- 拉最近 50–100 条；结果会**超出内联预算并落盘**，路径就在工具结果里。**读那个文件，别重拉**。
- 用 `execute_code` 解析，按 `id`（雪花 ID 单调递增）排序，打印 `时间 | 发送者 | 前 600~900 字`。
- 先按作者分组看数量：bot 的工具回显占了大半篇幅、信息量极低；精读**人类的消息**和**另一方给的结论消息**。
- 这类 thread 通常已跨过上下文压缩 ⇒ 它是唯一完整版；摘要里丢掉的数字，往往正是你要写进判据的那些。

### 2. 先找已有的共享产物，再决定建不建

- 列一遍共享 plan / 台账目录（本 profile：`workspace/plans/`），以及对方自己维护的 `PLAN.md`。
- 同一目标已有 → **续写它**；没有 → 才新建。同一目标两份真相 = 这套体系要消灭的东西。

### 3. 采证据：只花秒级

这些命令跑在**远端主机**上（NAS / 工作站）：那边只有 shell，本机的 `read_file` / `search_files` 够不着；
本机侧读、找文件照常用原生工具。

| 证据 | 怎么做 | 能证明什么 |
|---|---|---|
| 日志尾部 / 进度行 | `tail`、`grep -E '已处理\|进度\|完成'` | 在推进吗、速率、失败计数 |
| 进程存活 | 遍历 `/proc/[0-9]*/cmdline` 找脚本名 | 任务还活着 |
| 目录 / 对象计数 | 同一 `ls -1 … \| grep -c '<模式>'` **隔 20 秒测两次** | 差值 ⇒ 速率；同时证明进程活着 |
| 交付物存在性 | 对**具体路径** `ls -l` / `stat` | 试点 / 产物真的到位 |

- **进程存活别用 `ps | grep <脚本名>`**：busybox 系（NAS shell）的 `ps` 把命令截断成进程名，得到假阴性，
  读起来像「任务死了」。
- **全库扫描先算成本**：`du`、`find …/objects`、对数万文件逐个 `stat` 在弱 NAS 上要十几分钟，还会饿死
  对方正在跑的进程。只要一个数就换只读单点：一次 `ls` 一个目录、`wc -l`、抽 10 个条目乘一下。
- macOS 上没有 GNU `timeout`：ssh 侧用 `perl -e 'alarm shift; exec @ARGV' 60 ssh …` 兜住，否则挂死就不返回。

### 4. 复核时先排除两个假警报

- **名字不符合你的假设 ≠ 异常**：判「外来目录」前先确认命名规则。git-annex 的 hashdir 是 base62
  （`0G` / `2z` / `Pk` 都合法），不是两位十六进制 —— 用 `^[0-9a-f]{2}$` 过滤会把大批合法目录算成
  「有人在写这个库」，凭空造出一场数据危机。自检：把「异常」样本按名字长度 / 字符集分布打出来。
- **用 mtime 判时段，不要用推断链**：一次 `ls -ld` 抽几个样本就能定「这批写入属于哪个时间窗」；
  从脚本逻辑反推「它应该写了什么」不顶事 —— 用户对自己机器上亲眼所见现象的观察优先于你的推断。
- **内容寻址库里 `Directory not empty` 不是数据丢失**：同一个 key 可以合法地存在于多个冲突副本里，
  把一个条目 `mv` 到已存在同名非空**目录**上必失败。这是「发现了一个该修的缺陷」，不是「数据没了」——
  别据此宣布损失。

### 5. 落盘 + 一条回复

- 状态落进共享产物时带上**来源与时刻**（「10:26 实测：剩余 N，20 秒 −65 ⇒ ~195/分」）；任务在跑时，
  速率和判据比绝对值活得久。
- 补记过去的事用真实时间戳，不要假装是现在；数字当天拿不到就写「待确认」。
- 回复只做三件事：**结论先行 → 实测数字 → 一条「该谁动」的动作（步骤 / 块 id）+ 共享产物的绝对路径**。
- 你这条回复本身就是 thread 里的一条消息 ⇒ 不要再补发一条内容几乎相同的提醒，双份 = 噪音。
- 挑「下一步」时，优先挑**让正在跑的那条线能正确收尾**的那一块（对方脚本有已知缺陷 ⇒ 建「修缺陷 +
  幂等续跑」，判据写「失败计数不再增长」），而不是另起一条新工作线。

## 常见错误

- 跟执行方抢同一条消息 / 同一个动作 ⇒ 两个 bot 各答一遍，用户要读两遍。
- 把「读得到的」当成「发生了的」：只凭读日志的感觉报进度，没测过的也写成事实。
- 为了拿一个数去跑全库统计，把对方正在跑的任务饿死。
- 建第二份 plan / 第二份台账，让下一个接手的人不知道该信哪份。
